| UC-01 | Ingresar evidencia de un caso | Sistema del cliente (vía API) / Operador (carga manual) / Proceso periódico (casilla o carpeta) | La organización tiene al menos un canal de ingesta habilitado [Cap 2.4] | 1) El actor envía evidencia por API, carga manual desde el navegador, o esta llega a una casilla/carpeta que la plataforma revisa periódicamente [Cap 2.4]. 2) La plataforma verifica que el archivo sea legible y utilizable [Cap 2.4]. 3) Si es la primera evidencia sobre el hecho, el sistema crea un Caso con identificador único, propio y permanente [Cap 3]. 4) Si el caso ya existe, el sistema asocia la evidencia nueva al caso existente [Cap 2.4]. 5) El sistema registra el evento en el Rastro de Auditoría [Cap 2.11] | Si el archivo no es legible o utilizable, el sistema lo rechaza y comunica la razón en lenguaje comprensible para alguien no técnico, en vez de fallar en silencio [Cap 2.4]. | UC-02 | Procesar caso automáticamente y decidir | Sistema (motor de análisis multimodal) | El caso tiene evidencia legible; el flujo vigente tiene al menos un módulo de análisis activo [Cap 3]; existe una configuración de umbrales para la organización [Cap 2.6] | 1) El sistema ejecuta los módulos de análisis activos del flujo sobre la evidencia [Cap 2.5, 2.9]. 2) Cada módulo produce una o más señales [Cap 2.6]. 3) El sistema calcula el puntaje de confianza (0-100) con su desglose de componentes [Cap 2.6]. 4) El sistema compara el puntaje contra los umbrales configurados [Cap 2.6]. 5) Si el puntaje supera el umbral de aprobación y no hay señal de fraude activa, el sistema aprueba el caso automáticamente [Cap 2.6, DEC-07]. 6) El sistema registra la decisión, su razón y el rastro de auditoría [Cap 2.11] | Si el puntaje cae en rango intermedio, o una señal individual está bajo su mínimo aunque el total lo permita, el caso se deriva a revisión asistida [Cap 2.6, 2.7]. Si un módulo falla o no está disponible, el caso se deriva a revisión indicando qué faltó, nunca se aprueba con información parcial [Cap 3]. | UC-04 | Diseñar y publicar un flujo | Diseñador de Flujo | El actor tiene permiso de rol Diseñador de Flujo en su organización [Cap 2.13] | 1) El diseñador arma el proceso arrastrando y conectando bloques: ingesta, análisis, cálculo de puntaje, reglas, decisión e integraciones [Cap 2.8]. 2) El diseñador configura cada bloque sin escribir código [Cap 2.8]. 3) El diseñador prueba el flujo sobre casos de ejemplo y observa el resultado paso a paso [Cap 2.8]. 4) El diseñador publica el flujo [Cap 2.8]. 5) El cambio queda disponible en producción en segundos, y los casos nuevos se procesan con la versión publicada [Cap 2.8] | Un flujo publicado no puede modificarse en producción: se crea una versión nueva, se prueba y se publica; los casos en curso terminan con la versión con que empezaron [Cap 3]. ## Notas de trazabilidad

- Cada paso cita su fuente entre corchetes: `Cap X.Y` (documento de proyecto), `DEC-0N` (bitácora de decisiones), o `ENTn — Nombre` (entrevista).
- `null` se usó únicamente donde el texto fuente no describe explícitamente una ruta alternativa o de excepción para ese caso de uso — no se inventó ninguna.
- Los 18 casos de uso cubren las 18 entidades del Modelo de Dominio (`ModeloDominio_MIRA.md`): cada entidad participa en al menos un caso de uso como objeto de una operación (crear, modificar, consultar, exportar, eliminar).
- Actores primarios provienen literalmente de las categorías descritas en el Cap. 2.3 ("A quiénes sirve"): operador, supervisor, diseñador de flujo, compliance/riesgo, integrador técnico del cliente, y del lado DPRIME: soporte/operación, ingeniería de modelos, comercial/administración.
