La columna **Verificación** contiene un criterio medible solo cuando el texto del caso de uso lo permite; en caso contrario se indica `null` explícitamente, sin inventar un umbral que el texto no da.

## Notas metodológicas

- **Alcance deliberadamente acotado:** estos requisitos se derivaron *solo* de los 18 casos de uso (`CasosDeUso_MIRA.md`), no directamente del documento de proyecto ni de las entrevistas. Como consecuencia, varias condiciones no funcionales del documento original (disponibilidad 99,9%, tiempo de carga de pantalla &lt;2s, cifrado en tránsito/reposo, residencia de datos en Chile, ambientes separados, restauración de respaldos, idioma de la interfaz) **no aparecen aquí** porque no fueron formuladas como paso o precondición de ningún caso de uso de la lista — quedan fuera de este artefacto por diseño, no por olvido.
- **Prioridad (MoSCoW):** el documento fuente no entrega una escala de prioridad, por lo que el equipo declara el siguiente criterio de asignación y lo aplica de forma uniforme:
  - **Must** — sin el requisito la marcha blanca con el cliente piloto no puede iniciarse, *o* es exigencia legal/regulatoria sostenida por un interesado con poder de veto (Compliance), *o* es una regla de negocio absoluta del Cap. 3 cuyo incumplimiento produce una decisión inválida o no auditable.
  - **Should** — necesario para operar bien, pero admite una alternativa manual acotada durante la marcha blanca sin invalidar decisiones ni auditoría.
  - **Could** — mejora deseable, condicionada a que el cliente la habilite o comprometida para una entrega posterior, cuya ausencia no degrada la operación del piloto.
  - **Won't (esta versión)** — explícitamente fuera de alcance según el Cap. 5.1 del documento de necesidades: sistema de gestión de siniestros/admisión/originación, modelos de reconocimiento propios desde cero, aplicación móvil de captura para el asegurado, facturación electrónica y contabilización, y migración de casos de pilotos anteriores. No se listan como filas porque no son requisitos del sistema, sino frontera de alcance.
  - Distribución resultante: **36 Must / 15 Should / 4 Could** en requisitos funcionales y **7 Must / 1 Should / 2 Could** en no funcionales.
- **Verificación `null`:** se usó únicamente cuando el caso de uso no ofrece ningún número, umbral o regla binaria a partir de la cual construir un criterio de aceptación objetivo (por ejemplo, calificar qué tan "comprensible" es un mensaje de error, o cuánta anticipación debe tener una alerta de plazo).
